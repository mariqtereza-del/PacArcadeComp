# Pac-Man PC Port Plan, version 3.0 (2026-10-23)
Authoritative roadmap. Generated by tools/make_plan.py from tools/plan_data.py. Do not hand-edit this file; edit the data file and regenerate.
The user-facing version is docs/Pac-Man_PC_Port_Plan.html (also published as an artifact).

## What the project is
- A Windows player for the 1980 arcade maze game that plays exactly like the arcade board: every ghost rule, speed, quirk and bug, frame for frame, including level 256. It needs your own copy of the arcade ROM (pacman.zip); nothing from it is in the project.
- Release 1.0 (S36) was an emulator: the arcade program ran on a Z80 core. Release 1.1.0 added the readable rules and modding. Release 2.0.0 (N55) is native: the program has no Z80 inside; the game is C++ proved identical to the original, frame by frame and cycle by cycle. Your ROM is only read for data tables (maze, text, levels, graphics, sound).
- Around the game there are modern extras you can turn off or reset: menus, pads, save states, rewind, records, achievements, CRT looks, stats, a Cheats page (invincibility; using it switches records and achievements off).
- Honest limit: 24 of the original routines (random numbers, scoring, dots, ghost targeting, movement, timers, ghost house) are readable C++ you can edit (src/logic). Most of the rest of the game is an exact generated translation (src/game/attract_prog.h): correct and proved, but not written as readable rules.

Approach, as it turned out: Track A built a C++ emulator of the board that ran the player's own ROM (S01 to S37, release 1.0), wrapped in a modern PC front end. Track B/C rewrote the main rules as readable C++ and made them switchable (T01, T02; release 1.1.0). Track D (N00 to N55) replaced the whole original program with native C++ proved identical frame by frame and removed the Z80 from the program (release 2.0.0). The ROM is never bundled; its data tables are read at run time. Modern features live outside the accuracy core.
Reference oracles: the Python prototype in tools/analysis (S05) and, since N50, the Z80 reference in tests/oracle. Every step is compared against one of them or against ROM data or documented arcade values.

Status now: 164 steps. VERIFIED 164. Scrapped (removed or replaced, listed below): 31.

## Rules for every step
1. One primary objective per step.
2. Read only the files the step names. Do not re-read the whole project.
3. Verify before extending: run the step's VERIFY. Code written is not a finished step.
4. Never build on an unverified step. If S(n) fails, fix S(n) before S(n+1).
5. Never redo VERIFIED work. Replacing working code needs a written reason plus regression tests.
6. Checkpoint after every step: update PROJECT_STATUS.md, the plan status, evidence, known limits, next step.
7. Keep each step small enough to finish inside one context. If it looks big, split it before starting.
8. Spend tokens on inspecting, implementing, testing, fixing, documenting. No long tutorials.
9. Do not ask the user technical questions. Investigate, choose the safest option, record the decision. Ask only for human decisions or information only the user has.
10. Never claim success without evidence. 'It compiles' and 'a window opened' do not prove hardware is emulated correctly. Prefer exact comparison against the prototype oracle, ROM data, or documented arcade values.
