How it works: hooks sit on all 17 instructions of the loop and on the start. At the loop head 2A38 whole rounds (one tile: 108 T-states, 88 to 122 when the tile is replaced) run in one go while they end before the 50,688-cycle limit; every other instruction (and the head when its round does not fit) runs by itself, exactly like the ROM instruction (registers, flags, WZ, R, T-states). The frame can therefore end between any two instructions and the interrupt arrives at exactly the same place as in the original, and no ROM instruction of the loop runs any more.
Honest notes: (1) in the real coverage runs the loop only finds tiles to replace in rare cases; the replacing instructions 2A53 to 2A57 were not entered with real game states in these runs (proved by the isolated random cases, whose video RAM is full of such tiles, and the cut tests); (2) the progress meter here counts an address as executed only when no native hook handles it (or the hook ran the ROM instruction), because every instruction address of this loop is itself a hook; both numbers below use that same rule, so they are not comparable to the N12 to N18 meter numbers (which counted hook entry addresses).
Two small test-set-up faults were fixed while writing the test (a start state that runs round the whole address space, and the meter rule above); no fault in the native code was found by the comparisons except the opcode fetch count of the start (3 instead of 1), found by the first isolated run and fixed.
