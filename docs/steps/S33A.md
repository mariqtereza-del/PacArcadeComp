# STEP S33A: Design review and corrections (the user's list)
Status: **VERIFIED**   Lane: POLISH   Depends on: S33

OBJECTIVE: A planned pause in the building: you play the finished features as a normal player, write one list of everything you would change or add, and Claude sorts it into small numbered steps before the Options menu (S34) is built.

WHY: S34 builds the menu and the Purist-mode proof around the features as they are then; changes made later mean re-doing that proof. This is the cheapest moment for design corrections.

STARTING STATE: S31 to S33 verified by the user.

READ FIRST: PROJECT_STATUS.md; docs/steps/S31.md to S33.md

MAY TOUCH (only these): docs/ only (this step writes no code)

IMPLEMENT:
- 1. User plays freely for 20-30 minutes (no test script) and writes the list: for each item what they did, what they expected, what happened, what they would prefer, and a priority (must / nice / later).
- 2. Claude sorts every item into one of four boxes and writes the result in docs/DESIGN_REVIEW.md: (A) tuning of an existing feature (keys, messages, defaults): small fix step before S34; (B) behaviour of an existing feature (like the high-score rule): one numbered fix step each, with its own test; (C) new feature: goes into S34's menu if it needs a switch, otherwise onto the 'after 1.0' list; (D) anything that would change emulated behaviour: refused, or offered only as a labelled Assist that Purist mode turns off.
- 3. Claude adds the A and B items to the plan as numbered steps (S33B, S33C ...), each small and independently tested, and says what S34 will contain.
- 4. Claude lists open design questions it noticed itself (for example: settings not remembered between runs, volume control, pad buttons for pause and save, pausing when the window loses focus) and asks for a yes or no on each.

DO NOT:
- No code in this step.
- Do not change a VERIFIED step's evidence; fixes become new steps.

VERIFY:
- docs/DESIGN_REVIEW.md exists and every item is in exactly one box

SUCCESS CRITERIA: Every correction has a box, a step number or a reason for waiting.

IF FAILURE: Stop. Re-run only this step's VERIFY command. Undo the last edit and retry. Compare against the Python prototype (tools/analysis) as the reference. Write what you found in docs/evidence/S33A_failure.md. Do not start the next step.

DOCUMENT: In PROJECT_STATUS.md set this step's row (status, date, evidence path), add a line under Changes and Known limitations, and set Next step. Set the status in tools/plan_data.py and run python3 tools/make_plan.py.

EVIDENCE TO RECORD: docs/DESIGN_REVIEW.md

CHECKPOINT: Run sh tests/run_all.sh (all earlier tests must still pass), then sh tools/checkpoint.sh S33A and send the zip to the user.

USER ACTIONS (tell the user in plain click-by-click words; see the Standard test routine in the plan page):
- Play 20 to 30 minutes freely and send one written list (what you did, what you expected, what happened, what you would prefer, must / nice / later).
